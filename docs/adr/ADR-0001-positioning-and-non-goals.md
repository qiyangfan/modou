# ADR-0001：定位、生态位与 Non-goals

- 状态：接受
- 日期：2026-10-14
- 依据：2026-10-14 四车道竞品调研（[docs/research-2026-10.md](../research-2026-10.md)）

## 决策

墨斗定位为**数据库工程化的本地层**：CLI 为体、MCP 为面的开发者工具，四个能力域——
变更验收（pack/verify）、SQL 优化（optimize）、规则审核（lint）、漂移洞察（patrol）。
四个差异化承诺，即四条产品线：

1. **交棒验收闭环**：给"开发交 SQL → 运维代执行"的既有流程外挂打包防漏 + 执行后机器
   验收——迁移工具（Atlas/Flyway/Skeema）假设工具自己执行，审核平台（Bytebase/Yearning）
   假设改用平台执行，全行业没人做这个交棒闭环。
2. **MySQL 侧的实证优化**：AI 索引建议必须过影子库实测复核；PG 侧已被 Postgres MCP Pro
   （HypoPG 假想索引）占位，MySQL 侧空白。
3. **SOAR 遗产的规则继承者**：小米 SOAR（8.8k★）事实停滞，现代化规则库无人维护。
4. **本地优先 + Agent 原生轻端**：平台重部署、CLI 无 Agent 入口（Atlas 刚开始补）。

**Non-goals（不做清单）**：

- 不做工单/审批平台——那是 Bytebase/DBdoctor 的正面战场，且与"零流程改造"承诺矛盾；
- 不做执行引擎——不替运维执行生产 SQL，不做 pt-osc/gh-ost 克隆（做集成建议，不做替代）；
- 不做 text-to-SQL/GenBI——WrenAI 赛道，问题域不同；
- 不追求全方言覆盖——MySQL 先行、PG 次之（ADR-0005），其他按需求排队；
- 不做云服务——schema 与真实 SQL 是高敏数据，信任红利在本地；
- 不做 ORM/schema-as-code 声明式范式——Atlas 领域；墨斗接受任意 SQL 变更集输入。

## 理由

调研实证的四个交叉空白（交棒闭环全空白 / MySQL 实证优化空白 / 本地+Agent 轻端空白 /
规则引擎无继承者）相互独立又共享同一套内核基建（快照+回放+报告），边际成本递减——
这是"四个承诺一个产品"成立的结构性原因。

## 后果

- 车道必须串行铺开：v0.1 只做变更车道，防止"超级项目"死于范围失控；
- 优化车道的 MySQL 实证要真建索引（无 HypoPG），是攻坚点也是壁垒（ADR-0005）。
