# Skill：数据库变更评审（墨斗委托工作流）

给宿主 Agent 的工作流模板：用墨斗（modou）的 MCP 证据原语完成一次数据库变更评审。
墨斗负责确定性证据（打包、影子库验收、规则审核、执行计划实证），你（宿主 Agent）
负责编排与语义判断。所有工具只在本地运行；验证/优化会拉起一次性容器化影子 MySQL。

## 结论分级（先读这个）

墨斗的每份报告只有两档结论：

- **实证已验证**：判定出自确定性代码与影子库实测，决定 `exit_code`
  （0=无发现 / 1=存在发现 / 2=环境或输入错误）；
- **AI 观点**：报告里单列的 `ai_opinions` 区（或文本报告的「AI 观点」区），
  来自可选的 BYOK 内置分析，**永远不影响退出码**。转述它们时必须保留「未实证」标注。

## 工作流

### 1. 打包变更集 → `pack`

- 输入：变更集目录（`V<序号>__<描述>.sql` + `manifest.txt`）。
- 看 `exit_code`：0=打包成功；1=校验拒绝（按 `warnings` 逐条向用户报告）；
  2=参数错误。
- `warnings` 里的 destructive / 锁风险预警要在评审意见里逐条点名——这是机器事实。

### 2. 采集执行前后快照 → `snapshot_capture`

- 执行前、执行后各采一次（运维执行变更集在两采之间，属于线下流程）。
- 返回的 `summary` 是元数据摘要（库 → 表清单 → 列/索引数）；需要全文结构时
  直接读取 `output` 指向的快照文件。

### 3. 影子库验收 → `verify`

- 输入：变更集目录 + 前后两份快照。墨斗在本地影子 MySQL 上回放变更集，
  与基线/实际三方比对。
- 解读 `report`：
  - `missing_execution`（漏执行）/ `wrong_execution`（错执行）/ `historical_drift`
    （历史漂移，非本次变更）按库分组，逐对象逐维度带期望/实际值；
  - `exit_code` 0=全部一致，1=存在差异，2=环境或输入错误；
  - 若配置了 BYOK（`MOUDO_AI_BASE_URL` / `MOUDO_AI_API_KEY` / `MOUDO_AI_MODEL`），
    报告附 `ai_opinions`（失败归因解释）；未配置时无该区，行为不变。

### 4. 静态规则审核 → `lint`

- 纯静态、无数据库连接。命中清单（`hits`）是机器事实，逐条转述。
- 配置 BYOK 时，规则零命中的「残留语句」会得到语义评审观点（同样只进
  `ai_opinions`，不碰退出码）。

### 5. 慢 SQL 优化实证 → `optimize`（可选）

- 输入：慢 SQL 语句文件 + 采样基线快照（`snapshot_capture --sample-rows` 采集）。
- 每个候选建议有两级状态：`measured`（影子库实测代价下降，附提升百分比）或
  `unverified`（附原因）。**只把 measured 级建议称为有效**；unverified 的说明原因。
- 配置 BYOK 时 AI 参与候选生成，但候选同样必须过影子实证关——来源不影响标准。

### 6. 跨信号综合 → `patrol_summarize`（可选）

- 输入：已生成的巡检报告文件（`--drift` / `--unused` / `--slowlog`，至少一份）。
- 得到跨信号 digest（`report_kind=patrol_summary`）；配置 BYOK 时附跨信号叙事观点。

## 红线（转述时不得越过）

1. 确定性结论与 AI 观点分开陈述，AI 观点必须带「未实证」标注；
2. 不建议「自动执行」任何修复——DROP 语句、索引删除语句等一律交给用户决定；
3. 快照与报告含生产 schema 元数据，不要把报告内容复制到外部服务；
4. `exit_code` 是唯一门禁依据：CI 卡点只看退出码，不看 AI 观点。
